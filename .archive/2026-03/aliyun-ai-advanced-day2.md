## Day 2 - 知識庫 RAG 高級應用

### 1. RAG 原理深度解析

#### 1.1 什麼是 RAG

**RAG (Retrieval-Augmented Generation)** = 檢索 + 生成

```
傳統 LLM:
用戶問題 → LLM → 回答
(僅依賴訓練數據)

RAG:
用戶問題 → 檢索知識庫 → 相關文檔 → LLM + 上下文 → 回答
(結合私有數據)
```

**為什麼需要 RAG:**
```
LLM 的局限性:
├─ 知識截止：訓練數據有時間限制
├─ 幻覺問題：可能編造信息
├─ 私有數據：無法訪問企業內部數據
└─ 成本問題：長上下文 token 消耗大

RAG 的優勢:
├─ 實時更新：知識庫可隨時更新
├─ 減少幻覺：基於真實文檔回答
├─ 私有數據：安全訪問內部知識
└─ 降低成本：只檢索相關片段
```

#### 1.2 RAG 工作流程

```
┌─────────────────────────────────────────────────────┐
│                    用戶問題                          │
│         "你們公司的退換貨政策是什麼？"                 │
└────────────────────┬────────────────────────────────┘
                     ↓
        ┌────────────────────────┐
        │   1. 問題向量化         │
        │   (Embedding 模型)      │
        └────────┬───────────────┘
                 ↓
        ┌────────────────────────┐
        │   2. 向量檢索           │
        │   (相似度匹配)          │
        └────────┬───────────────┘
                 ↓
        ┌────────────────────────┐
        │   3. 文檔重排序         │
        │   (Rerank 模型)         │
        └────────┬───────────────┘
                 ↓
        ┌────────────────────────┐
        │   4. 構建提示詞         │
        │   (上下文 + 問題)        │
        └────────┬───────────────┘
                 ↓
        ┌────────────────────────┐
        │   5. LLM 生成回答       │
        │   (千問 Plus)           │
        └────────┬───────────────┘
                 ↓
        ┌────────────────────────┐
        │   6. 返回用戶           │
        │   "我們的退換貨政策..."   │
        └────────────────────────┘
```

#### 1.3 向量檢索原理

**向量化過程:**
```
文本 → Embedding 模型 → 向量（多維數組）

示例:
"退換貨政策" → [0.12, -0.45, 0.78, ..., 0.33] (1536 維)
```

**相似度計算:**
```
餘弦相似度 (Cosine Similarity):
similarity = cos(θ) = (A·B) / (||A|| × ||B||)

結果範圍：-1 到 1
- 1: 完全相同
- 0: 無關
- -1: 完全相反

實際應用:
- > 0.8: 高度相關
- 0.5-0.8: 中等相关
- < 0.5: 相關性低
```

**檢索策略:**
```yaml
Top K 檢索:
  說明：返回最相似的 K 個文檔
  推薦值：3-10
  場景:
    K=3-5: 精確問答
    K=5-10: 綜合性問題

閾值過濾:
  說明：只返回相似度高於閾值的文檔
  推薦值：0.6-0.8
  場景:
    0.8+: 高精度要求
    0.6-0.7: 一般問答
    <0.6: 寬鬆匹配

混合檢索:
  說明：向量檢索 + 關鍵詞檢索
  優勢：兼顧語義和精確匹配
  場景：專業術語、產品型號
```

### 2. 文檔分段策略

#### 2.1 分段的重要性

```
問題：為什麼需要分段？

❌ 不分段：
- 整個文檔作為一個向量
- 檢索精度低
- Token 消耗大
- 無關信息干擾

✅ 合理分段：
- 每段表達完整語義
- 檢索更精確
- Token 使用高效
- 減少干擾信息
```

#### 2.2 分段方法

**方法一：固定長度分段**
```yaml
配置:
  分段大小：500 tokens
  重疊：50 tokens
  
優點:
  - 簡單直接
  - 易於實現
  
缺點:
  - 可能切斷語義
  - 段落不完整
  
適用:
  - 長文本
  - 結構化程度低的文檔
```

**方法二：按結構分段**
```yaml
配置:
  按標題分段（H1/H2/H3）
  按段落分段
  按章節分段
  
優點:
  - 語義完整
  - 結構清晰
  
缺點:
  - 依賴文檔質量
  - 段落長度不一
  
適用:
  - 結構化文檔
  - 手冊、規範
```

**方法三：語義分段**
```yaml
配置:
  使用 NLP 模型識別語義邊界
  按主題變化分段
  
優點:
  - 語義連貫
  - 檢索精度高
  
缺點:
  - 計算成本高
  - 實現複雜
  
適用:
  - 高價值文檔
  - 專業知識庫
```

#### 2.3 分段最佳實踐

**推薦配置（百煉控制台）:**
```yaml
通用文檔:
  分段大小：500 tokens
  重疊：50 tokens
  分段方法：按結構 + 固定長度

技術文檔:
  分段大小：800 tokens
  重疊：100 tokens
  分段方法：按章節/小節

FAQ 文檔:
  分段大小：200 tokens
  重疊：20 tokens
  分段方法：按問題分段

對話記錄:
  分段大小：300 tokens
  重疊：30 tokens
  分段方法：按對話輪次
```

**分段質量檢查:**
```markdown
檢查清單:
- [ ] 每段表達完整語義
- [ ] 段落長度適中（200-1000 tokens）
- [ ] 重疊部分合理（10% 左右）
- [ ] 無孤立的短段落（<50 tokens）
- [ ] 標題/關鍵信息包含在段內

優化方法:
- 段落太長 → 減小分段大小
- 語義切斷 → 增加重疊
- 孤立段落 → 合併相鄰段落
- 檢索不準 → 調整分段策略
```

### 3. 重排序（Rerank）

#### 3.1 為什麼需要 Rerank

```
問題場景:
檢索返回 Top 10 文檔，但相關性參差不齊

示例:
用戶問："如何退貨？"

檢索結果（按向量相似度）:
1. [0.82] 退貨流程說明 ← 相關
2. [0.79] 換貨申請步驟 ← 相關
3. [0.75] 售後服務政策 ← 部分相關
4. [0.72] 商品質量標準 ← 不相關
5. [0.70] 物流配送說明 ← 不相關
...

問題:
- 前 5 條混入了不相關內容
- LLM 會被干擾信息影響
- 回答質量下降

解決方案:
使用 Rerank 模型重新排序
```

#### 3.2 Rerank 工作原理

```
第一階段：向量檢索（快速粗篩）
輸入：用戶問題
過程：計算向量相似度
輸出：Top 50 候選文檔
時間：<100ms

第二階段：Rerank 重排序（精細排序）
輸入：用戶問題 + Top 50 文檔
過程：交叉編碼器（Cross-Encoder）深度分析
輸出：重新排序的 Top 10 文檔
時間：100-500ms

最終結果:
1. [0.95] 退貨流程說明 ← 精確相關
2. [0.88] 換貨申請步驟 ← 高度相關
3. [0.75] 售後服務政策 ← 部分相關
4-10. ...
```

#### 3.3 百煉 Rerank 配置

**啟用 Rerank:**
```
1. 百煉控制台 → 知識庫 → 檢索配置
2. 開啟「重排序」開關
3. 選擇 Rerank 模型：
   - 通義千問 Rerank
   - BGE Rerank
   - 自定義模型
4. 設置返回數量：Top 5-10
5. 保存配置
```

**參數調優:**
```yaml
檢索配置:
  初始檢索數量：50 (Top 50)
  Rerank 後返回：5-10 (Top 5-10)
  相似度閾值：0.6
  
Rerank 閾值:
  > 0.8: 高度相關，優先使用
  0.6-0.8: 相關，可作為參考
  < 0.6: 相關性低，考慮過濾
  
性能優化:
  減少初始檢索數量 → 提高速度（但可能漏檢）
  增加初始檢索數量 → 提高召回率（但變慢）
```

**效果對比:**
```
不使用 Rerank:
- 檢索時間：50ms
- 回答準確率：75%
- 適合：簡單問答、快速響應

使用 Rerank:
- 檢索時間：300ms
- 回答準確率：90%+
- 適合：專業問答、高精度要求
```

### 4. 多知識庫融合

#### 4.1 為什麼需要多知識庫

```
場景：大型企業知識管理

單一知識庫的問題:
├─ 文檔混雜：產品、人事、財務混在一起
├─ 權限難控：所有人能看到所有內容
├─ 更新頻率低：審批流程長
└─ 檢索精度低：噪声多

多知識庫優勢:
├─ 分類清晰：按部門/業務劃分
├─ 權限精細：不同人訪問不同庫
├─ 獨立更新：各部門自主維護
└─ 檢索精準：針對性強
```

#### 4.2 知識庫架構設計

**按業務劃分:**
```
企業知識庫體系:
├─ 產品知識庫
│   ├─ 產品手冊
│   ├─ 規格參數
│   └─ 價格政策
│
├─ 售後知識庫
│   ├─ 退換貨政策
│   ├─ 維修流程
│   └─ 常見問題
│
├─ 銷售知識庫
│   ├─ 銷售話術
│   ├─ 競爭對手分析
│   └─ 成功案例
│
└─ 內部知識庫
    ├─ 人事制度
    ├─ 財務流程
    └─ IT 規範
```

#### 4.3 多知識庫檢索策略

**策略一：路由檢索**
```
用戶問題 → 意圖識別 → 選擇知識庫 → 檢索 → 回答

示例:
用戶："這個產品保修多久？"
  ↓
意圖識別：產品相關
  ↓
選擇：產品知識庫
  ↓
檢索並回答
```

**策略二：並行檢索**
```
用戶問題 → 同時檢索多個知識庫 → 合併結果 → Rerank → 回答

適用場景:
- 問題跨多個領域
- 不確定屬於哪個知識庫
- 需要綜合性回答
```

**策略三：分層檢索**
```
用戶問題 → 通用知識庫（第一層）
              ↓ (未找到)
         專業知識庫（第二層）
              ↓ (未找到)
         人工客服
```

#### 4.4 百煉多知識庫配置

**配置步驟:**
```
1. 創建多個知識庫
   - 產品知識庫
   - 售後知識庫
   - 銷售知識庫

2. 在應用中綁定多個知識庫
   應用配置 → 知識庫 → 添加多個

3. 設置檢索優先級
   - 產品知識庫：優先級 1
   - 售後知識庫：優先級 2
   - 銷售知識庫：優先級 3

4. 配置檢索策略
   - 檢索模式：並行檢索
   - 每個知識庫 Top K: 5
   - 合併後 Rerank: 開啟
   - 最終返回：Top 5
```

**權限管理:**
```yaml
知識庫權限:
  產品知識庫:
    可讀：全體員工
    可寫：產品部
    
  售後知識庫:
    可讀：客服團隊
    可寫：售後部
    
  銷售知識庫:
    可讀：銷售團隊
    可寫：銷售部
    
  內部知識庫:
    可讀：管理層
    可寫：HR/財務
```

### 5. 實戰：企業知識助手

#### 5.1 需求分析

**場景:** 科技公司內部知識助手

**功能需求:**
```
- 產品知識問答
- 技術文檔檢索
- 售後政策查詢
- 內部流程指引
- 權限控制訪問
```

**技術方案:**
```yaml
知識庫:
  - 產品知識庫（產品手冊、規格、價格）
  - 技術知識庫（API 文檔、開發指南）
  - 售後知識庫（政策、流程、FAQ）
  - 內部知識庫（制度、流程）

模型：千問 Plus
檢索配置:
  初始檢索：Top 50
  Rerank: 開啟
  最終返回：Top 5
  相似度閾值：0.6

權限控制:
  - 產品/技術/售後：全體員工
  - 內部：管理層
```

#### 5.2 知識庫準備

**文檔收集:**
```markdown
產品知識庫:
- 產品手冊.pdf (50 頁)
- 規格參數表.xlsx
- 價格政策 2026.docx
- 競爭對手對比.pptx

技術知識庫:
- API 文檔.md
- 開發指南.md
- 最佳實踐.md
- 常見技術問題.md

售後知識庫:
- 退換貨政策.docx
- 維修流程.pdf
- FAQ 大全.docx

內部知識庫:
- 員工手冊.pdf
- 財務報銷流程.docx
- IT 使用規範.md
```

**文檔預處理:**
```bash
# 1. 格式轉換
PDF → Markdown (保留結構)
Word → Markdown
Excel → Markdown (表格)
PPT → Markdown (提綱)

# 2. 清理內容
- 刪除頁眉頁腳
- 刪除無關圖片
- 修正格式錯誤
- 統一標題層級

# 3. 添加元數據
---
title: 產品手冊 - A 系列
department: 產品部
version: 2026.1
tags: [產品，規格，A 系列]
---
```

#### 5.3 創建知識庫

**步驟 1：創建產品知識庫**
```
1. 百煉控制台 → 知識庫 → 創建
2. 填寫信息：
   - 名稱：產品知識庫
   - 描述：產品手冊、規格、價格
   - 嵌入模型：text-embedding-v3
3. 上傳文檔：
   - 產品手冊.pdf
   - 規格參數表.xlsx
   - 價格政策 2026.docx
4. 分段配置：
   - 分段大小：500 tokens
   - 重疊：50 tokens
   - 分段方法：按結構
5. 開始處理（等待完成）
```

**步驟 2：創建其他知識庫**
```
重複步驟 1，創建:
- 技術知識庫
- 售後知識庫
- 內部知識庫
```

#### 5.4 配置應用

**創建知識助手:**
```
1. 百煉控制台 → 應用構建 → 創建應用
2. 選擇「智能體應用」
3. 基礎配置：
   - 名稱：企業知識助手
   - 模型：千問 Plus
   - 溫度：0.5（更準確）
4. 綁定知識庫：
   - 產品知識庫（優先級 1）
   - 技術知識庫（優先級 2）
   - 售後知識庫（優先級 3）
   - 內部知識庫（優先級 4）
5. 檢索配置：
   - 初始檢索：Top 50
   - Rerank：開啟
   - 最終返回：Top 5
   - 相似度閾值：0.6
```

**System Prompt:**
```markdown
# 角色定義
你是「企業知識助手」，負責回答員工關於產品、技術、售後和內部流程的問題。

# 知識範圍
你可以訪問以下知識庫：
1. 產品知識庫：產品手冊、規格、價格
2. 技術知識庫：API 文檔、開發指南
3. 售後知識庫：退換貨政策、維修流程
4. 內部知識庫：員工手冊、財務流程、IT 規範

# 工作流程
1. 理解用戶問題類型
2. 從對應知識庫檢索相關文檔
3. 基於檢索到的文檔回答
4. 如知識庫中沒有相關信息，如實告知

# 回答規範
- 基於知識庫內容回答，不要編造
- 引用具體文檔名稱（如「根據產品手冊...」）
- 不確定的信息如實告知
- 涉及權限的內容，提醒用戶權限要求

# 權限提醒
- 普通員工：可訪問產品/技術/售後知識庫
- 管理層：可訪問所有知識庫
- 如用戶詢問內部知識庫內容但無權限，禮貌提醒
```

### 掌握的要點

| 模塊 | 核心技能 |

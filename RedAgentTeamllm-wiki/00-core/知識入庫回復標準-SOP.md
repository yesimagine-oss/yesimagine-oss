## 標準回復格式（必須遵循，≤150 字）

```markdown
**知識**: [知識名稱，一句話說明]
**問題**: [解決什麼問題/場景]
**來源**: [URL]
**主題**: [分類類別]
**資產**: [X Genes + Y Capsules]
**置信度**: [0.XX]
**入庫**: ✅ `raw/` + `wiki/[path]/`
**Git**: `[commit_hash]`
**查重**: ✅ 已搜索
**狀態**: [🟢/🟡/🔴]
```

**原則:** 結論優先，表格代替文字，≤150 字

---

## 字段說明

| 字段 | 說明 | 示例 |
|------|------|------|
| **來源** | 知識來源 URL 或說明 | `https://github.com/...` 或 `用戶提供` |
| **資產** | 生成的 Gene 和 Capsule 數量 | `0 Genes + 0 Capsules` |
| **置信度** | 0-1 數值，基於證據 | `0.5`（僅原文）、`0.9`（原文 + 實測） |
| **GDI** | 基因完整性評分（0-100） | `85` 或 `待計算` |
| **評分** | 整體質量評分（0-10） | `8.5/10` |
| **入庫** | 實際存儲路徑 | `10-raw/` + `01-openclaw/` |
| **Git** | 提交 hash | `abc1234` |
| **狀態** | 入庫狀態 | `🟢完成`、`🟡待深度`、`🔴有問題` |

## 入庫原則

| 原則 | 說明 | 違反後果 |
|------|------|----------|
| **無原文不入庫** | 必須有真實來源原文 | 🔴 刪除文件 |
| **無實測不生成 Gene** | Gene 需要實測驗證 | 🟡 標註候选 |
| **無實測不生成 Capsule** | Capsule 需要執行證據 | 🟡 標註候选 |
| **真實性第一** | 禁止編造任何內容 | 🔴 事故記錄 |
| **分類清晰** | 按主題放入正確目錄 | 🟡 重新分類 |
| **報告完整** | 必須有入庫報告 | 🟡 補齊報告 |
| **回復≤100 字** | 符合 reply-sop.md | 🟡 精簡 |
| **雙來源流程** | 外部 + 內部事故 | ✅ 遵循 sampling-dedup-sop |

## 入庫流程（雙來源）

### 來源 1：外部知識

```
1. 原始采樣 → 10-raw/
   ↓
2. 查重 → 搜索知識庫，確認無重複
   ↓
3. 知識提煉 → 主題目錄
   ↓
4. 合併 → 如有重複，合併內容
   ↓
5. 修復 → 發現錯誤，修復優化
   ↓
6. 生成資產 → genes/ + capsules/
   ↓
7. 入庫報告 → 06-reports/
   ↓
8. Git 提交 → 記錄 commit_hash
   ↓
9. 標準回復 → ≤100 字
```

### 來源 2：內部事故

```
1. 事故記錄 → .learnings/
   ↓
2. 復盤分析 → 提煉教訓
   ↓
⚠️ 3. 用戶確認 → 是否提煉為 Gene
   ↓
4. 生成 Gene → genes/
   ↓
5. 驗證 → 標準檢查
   ↓
6. 查重 + 合併 → 避免重複
   ↓
7. 自動入庫 → wiki/
   ↓
8. Git 提交
```

## 查重規則

| 情況 | 處理方式 |
|------|----------|
| **完全重複** | 刪除重複文件，保留一個 |
| **部分重複** | 合併內容，刪除重複文件 |
| **主題重複** | 移動到正確目錄 |
| **名稱重複** | 重命名（添加日期或版本） |

### 查重命令

```bash
# 搜索關鍵詞
grep -ri "關鍵詞" /home/admin/.openclaw/workspace/RedAgentTeamllm-wiki/ --include="*.md"

# 搜索相似文件名
find /home/admin/.openclaw/workspace/RedAgentTeamllm-wiki/ -name "*關鍵詞*.md"

# 搜索相同內容
md5sum /home/admin/.openclaw/workspace/RedAgentTeamllm-wiki/**/*.md | sort | uniq -d
```

## 合併規則

| 情況 | 合併方式 |
|------|----------|
| **同一主題多個文件** | 合併為一個文件，保留所有內容 |
| **不同版本** | 保留最新版本，舊版本歸檔 |
| **互補內容** | 合併，標註來源 |
| **衝突內容** | 保留高可信度內容，標註爭議 |

## 最優選擇規則（查重/合併時強制執行）

### 評估標準（優先級從高到低）

| 優先級 | 標準 | 權重 | 說明 |
|--------|------|------|------|
| **1** | 可信度 | 40% | 原文 + 實測 (0.9+) > 僅原文 (0.5-0.8) > 候选 (0.1-0.4) |
| **2** | 完整性 | 25% | 內容完整 > 部分完整 > 碎片化 |
| **3** | 時效性 | 15% | 最新日期 > 舊日期 |
| **4** | GDI 評分 | 10% | GDI 95+ > GDI 80-94 > GDI <80 |
| **5** | 用戶評分 | 10% | 9/10+ > 7-8/10 > <7/10 |

### 最優選擇決策流程

```
1. 比較可信度 → 高者勝
   ↓ (如相同)
2. 比較完整性 → 完整者勝
   ↓ (如相同)
3. 比較時效性 → 最新者勝
   ↓ (如相同)
4. 比較 GDI 評分 → 高者勝
   ↓ (如相同)
5. 比較用戶評分 → 高者勝
   ↓ (如相同)
6. 合併兩者 → 保留所有獨特內容
```

### 示例

| 文件 A | 文件 B | 最優選擇 | 理由 |
|--------|--------|----------|------|
| 可信度 0.9，2026-04-20 | 可信度 0.5，2026-04-24 | **文件 A** | 可信度優先於時效性 |
| 可信度 0.8，完整 | 可信度 0.8，部分 | **文件 A** | 完整性更高 |
| 可信度 0.9，GDI 85 | 可信度 0.9，GDI 95 | **文件 B** | GDI 更高 |
| 內容互補，無衝突 | 內容互補，無衝突 | **合併** | 保留所有獨特內容 |

### 強制規則

| 規則 | 說明 |
|------|------|
| **可信度 <0.5 不入庫** | 除非標註為「候选」 |
| **有實測優先於無實測** | 實測證據 > 僅原文 |
| **權威來源優先於未知來源** | 官方文檔 > 第三方博客 |
| **合併時保留所有來源** | 標註每個內容的來源 |
| **衝突時標註爭議** | 不確定時如實標註 |

### 最優選擇回復格式

```markdown
**查重結果**: 發現 X 個相似文件
**最優選擇**: 保留 [文件名]（可信度 0.9，GDI 92，2026-04-24）
**合併**: 已合併 [文件名 B] 的獨特內容（X 條）
**歸檔**: [文件名 C] 已移動到 11-archive/
```

### 合併命令

```bash
# 合併多個文件
cat file1.md file2.md > merged.md

# Git 合併
git merge --no-ff branch-name
```

## 修復與優化規則

| 情況 | 修復方式 |
|------|----------|
| **錯誤內容** | 修正錯誤，記錄事故 |
| **不完整內容** | 補充缺失部分 |
| **格式錯誤** | 修正格式，符合 SOP |
| **分類錯誤** | 移動到正確目錄 |
| **低質量內容** | 優化或歸檔 |

### 修復流程

1. 發現錯誤
2. 記錄到 `.learnings/`
3. 修復內容
4. Git 提交
5. 更新入庫報告
